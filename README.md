# xui-fleet

Автоматизация 3x-ui: главная панель на RU-сервере, зарубежные ноды, каскад RU → нода
и одна подписка со всеми подключениями. Новый сервер добавляется одной командой.

```
                      подписка (одна ссылка)
клиент ───────────────► RU мастер (3x-ui, главная панель)
   │                        │  управляет нодами по API (HTTPS + pin сертификата)
   │  каскад: RU:8443 ──────┼──────────► 🇩🇪 нода de-1 :443 ──► интернет
   │  каскад: RU:8444 ──────┼──────────► 🇳🇱 нода nl-1 :443 ──► интернет
   └─ прямое: de-1:443, nl-1:443 (опционально)
```

Для каждой ноды пользователь получает в подписке два подключения: каскадное
(через RU) и прямое. Всё построено на штатных возможностях 3x-ui v3 (встроенные ноды,
API-токены, автоустановка), поэтому панель остаётся обычной панелью: ею можно
пользоваться руками, сервис её не ломает.

## Установка

1. Скачайте `xui-fleet-…zip` со страницы [Releases](https://github.com/airflech/xui-fleet/releases/latest).
2. Распакуйте и запустите файл для своей системы (таблица ниже).
3. Дальше приложение обновляется само: проверяет релизы при запуске и раз в 30 минут.

Новая версия выходит тегом `vX.Y.Z` (номер должен совпадать с `src/xui_fleet/__init__.py` и `pyproject.toml`):
GitHub Actions прогоняет тесты на Python 3.9 и 3.12 и публикует архив с контрольной суммой.

## Запуск (интерфейс в браузере)

Работает на **Windows, macOS и Linux**. Ничего заранее ставить не нужно: если на компьютере нет Python,
файл запуска предложит установить его и после согласия поставит сам (Windows — winget или подписанный
установщик с python.org, только для текущего пользователя; macOS — «Инструменты разработчика» Apple;
Linux — пакетный менеджер дистрибутива с запросом пароля). Остальные зависимости ставятся автоматически.
Папку проекта можно положить куда угодно (в том числе на флешку или в облако) и запустить:

| Система | Что запустить |
| --- | --- |
| macOS | «Запустить xui-fleet.command» (двойной клик) |
| Windows | «Запустить xui-fleet.bat» (двойной клик) |
| Linux | «Запустить xui-fleet.sh» (`sh "Запустить xui-fleet.sh"`) |

Первый запуск (и первый запуск после переноса папки) сам готовит окружение, затем интерфейс работает в фоне
на постоянном адресе и открывается в браузере; окно запуска можно закрыть. Рядом появляется ярлык
«Открыть xui-fleet». Данные этого компьютера (бэкапы главного сервера, ключ адреса интерфейса): macOS —
`~/Library/Application Support/xui-fleet`, Windows — `%APPDATA%\xui-fleet`, Linux — `~/.local/share/xui-fleet`.

### Профили и выход

Профиль — отдельный набор серверов со своими доступами, бэкапами и синхронизацией (как контексты kubectl или
профили AWS CLI). Переключатель — кнопка с именем профиля в шапке; «Новый профиль» открывает окно первого запуска.
Первый профиль («Основной») — это прежнее расположение данных: `fleet.yaml` рядом с программой, бэкапы и настройки
синхронизации — в папке данных, поэтому при обновлении ничего не переносится. Остальные профили — в `profiles/<id>/`
рядом с программой и `profiles/<id>/` в папке данных; список — `profiles.json`. Консольные команды работают с
активным профилем.

«Выйти из профиля» стирает его данные с этого компьютера: настройки, SSH-пароли, ключи панелей, бэкапы главного
сервера, настройки и пароль синхронизации (подтверждение — название профиля). Серверы и копия на сервере
синхронизации не меняются. «Стереть всё с этого компьютера» — то же для всех профилей, затем окно первого запуска.
Остаются только программа, её настройки обновления и адрес интерфейса.

### Несколько компьютеров (синхронизация)

«Бэкапы» → «Синхронизация между компьютерами» → «Включить…»: выберите сервер (главный или зарубежный) и пароль.
Данные приложения хранятся на нём в `/root/.xui-fleet-sync` зашифрованными (AES-256-GCM, ключ из пароля),
изменения отправляются через несколько секунд, другие компьютеры забирают их при запуске и раз в минуту.
Хранятся 10 последних версий; при одновременных изменениях побеждает последнее, предыдущее остаётся в истории.
Новый компьютер: «Подключить к синхронизации…» на первом экране (адрес сервера, SSH-доступ, пароль синхронизации).
Если хранить на зарубежном сервере, туда же уходят 3 последних бэкапа главного сервера.

### Обновление приложения

При включённой синхронизации обновления приходят сами. Номер версии — в `src/xui_fleet/__init__.py` и
`pyproject.toml` (`xui-fleet version`). Компьютер с более новой версией выкладывает программу на сервер
синхронизации (`/root/.xui-fleet-sync/app`, зашифровано и подписано паролем синхронизации), остальные при
запуске или в течение минуты ставят её и перезапускаются; зависимости переустанавливаются, только если
изменился их список. Данные помечены версией, которая их записала: более старое приложение не принимает и
не отправляет их, пока не обновится.

### Перенос на другой компьютер (файлом)

«Бэкапы» → «Копия приложения» → «Сохранить копию…»: один файл `.xfleet` под вашим паролем — настройки,
SSH-доступы, ключи панелей и бэкапы главного сервера. На новом компьютере запустите приложение и нажмите
«Восстановить из копии приложения…» (или «Бэкапы» → «Восстановить…»). Консоль: `xui-fleet app-export файл.xfleet`
и `xui-fleet app-import файл.xfleet`. Без пароля копию не открыть, восстановить пароль нельзя.

## Статистика пользователей и лимиты

Вкладка «Пользователи»: у каждого — трафик за всё время, число устройств и IP-адресов, серверы, через которые он
подключён сейчас. Клик открывает карточку: устройства (модель, ОС, приложение, первый и последний раз), IP-адреса с
сервером, лимиты устройств и IP. Всё берётся из главной панели 3x-ui (v3): `/clients/list/paged`,
`/clients/onlinesByGuid`, `/clients/clientIpsByGuid`, `/clients/hwids/<email>`, `/clients/ips/<email>`.

- Устройства (HWID) регистрируются, когда приложение с идентификатором устройства (Happ, v2RayTun, INCY) обновляет
  подписку. Лимит устройств (`limitHwid`) не пускает лишние устройства к подписке; «Забыть» освобождает место.
- Уже скопированный конфиг лимит устройств не остановит — для этого лимит IP (`limitIp`): лишние одновременные
  адреса 3x-ui отключает на время.
- Лимиты хранятся в панели: `fleet.yaml` задаёт их только новым пользователям, «Применить» их не перезаписывает.
- Трафик Xray считает на пользователя, не на отдельное подключение.

## Единый набор подключений

Для каждой зарубежной ноды сервис ведёт одинаковый набор (в подписке именно в этом порядке):

| Название | Что это |
| --- | --- |
| «🇬🇧 UK · через RU» | каскад VLESS Reality TCP, вход на главном сервере (по умолчанию выключен у нод, где RU-IP «замораживает» TCP: `set.cascade_tcp`) |
| «🇬🇧 UK · через RU (XHTTP)» | каскад: XHTTP + VLESS Encryption + Vision + XMUX на главном сервере, маскировка под собственный домен (сайт-заглушка nginx) |
| «🇬🇧 UK · через RU (Hysteria2)» | каскад по QUIC/UDP, сертификат домена |
| «🇬🇧 UK · через RU → WARP» | RU → нода → Cloudflare WARP: выход в интернет с адреса Cloudflare |
| «🇬🇧 UK» | напрямую: VLESS Reality TCP + Vision |
| «🇬🇧 UK · XHTTP» | напрямую: XHTTP + VLESS Encryption + Vision + XMUX |
| «🇬🇧 UK · Hysteria2» | QUIC/UDP с обфускацией salamander, сертификат ноды закреплён в ссылке |
| «🇬🇧 UK · WARP» | напрямую на ноду (Hysteria2), выход через Cloudflare WARP |

Что сделано против блокировок (по отчётам осени 2026 и замерам с домашнего Wi-Fi):

- **XHTTP + VLESS Encryption** (ML-KEM-768 + X25519) **+ Vision + XMUX**. Внутри Reality больше нет
  узнаваемого «TLS в TLS», а XMUX раздаёт трафик по нескольким соединениям и регулярно их меняет —
  ТСПУ не за что «заморозить». На IP хостинга, где обычный TCP встаёт после ~20 КБ, — 70–130 Мбит/с.
- **Маскировка под соседний сайт.** Reality у нод заимствует TLS-рукопожатие у настоящего сайта из
  той же подсети (TLS 1.3, h2, имя указывает на этот адрес), а не у www.microsoft.com. Сайт подбирается
  сам при подключении к ноде, раз в сутки проверяется и при необходимости меняется. Явный
  `direct.reality.target` в конфиге имеет приоритет.
- **Отпечаток firefox** вместо chrome во всех ссылках Reality.
- **Вход на RU-сервере** выдаёт себя за собственный домен (self-steal), поэтому IP и имя совпадают.

**Шаблон.** Набор задаётся один раз в `defaults.set` в `fleet.yaml`, и любой новый сервер получает ровно его
(окно «Добавить сервер» показывает, что будет создано). У отдельного сервера в `set` можно переопределить
только нужные поля — остальное по-прежнему берётся из шаблона. Вместе с подключениями новый сервер сам
получает маскировку под соседний сайт, собственную регистрацию WARP и сайт-витрину на http://IP/.

Существующие XHTTP-подключения обновляются на месте (ключи и путь сохраняются) — пользователям
достаточно обновить подписку. Любое подключение можно выключить (`defaults.set` или `set` у ноды:
`xhttp`, `xhttp_encryption`, `hysteria2`, `cascade_tcp`, `cascade_xhttp`, `cascade_hysteria2`, `warp`,
`cascade_warp`) или скрыть из подписки в окне «Название». Свободные порты подбираются сами;
порты панели, подписки и сайта-заглушки на главном сервере никогда не занимаются, а если Xray
на главном сервере после изменений не запустился, сервис убирает мешающее подключение и сообщает об этом.

Старые подключения ноды скрываются из подписки командой
`xui-fleet hide-legacy --node ИМЯ --keep тег[=Новое название]` — они продолжают работать у тех,
кто ещё не обновил подписку, удалить их можно в панели позже.

## Российские сайты — напрямую

- **На главном сервере.** Всё, что пользователь открывает через подключения «через RU», к российским
  сайтам (домены .ru/.su/.рф и другие российские зоны, `geosite:category-ru`, российские IP) уходит
  прямо с главного сервера, а не через зарубежную ноду: сайты видят российский адрес, ноды не тратят канал.
  Имена на сервере не резолвятся — российский DNS может подменять ответы для заблокированных сайтов.
- **На устройстве (Happ, INCY).** Подписка передаёт профиль маршрутизации «RU напрямую»: российские
  сайты идут мимо VPN совсем, остальное — через VPN; российские имена резолвит Яндекс DNS, остальные —
  Cloudflare через туннель. Профиль появляется в Happ при обновлении подписки.

Настройки в `fleet.yaml`:

```yaml
routing:
  ru_direct_on_master: true   # российское — напрямую с главного сервера
  client_profile: true        # профиль «RU напрямую» для Happ в подписке
  extra_direct: [domain:example.com, geoip:by]   # ещё что-то напрямую
```

## Сайты-витрины

Чтобы домен и IP-адреса не вызывали вопросов, на каждом сервере открывается обычный сайт небольшой
компании (бренды вымышленные, тема подбирается по имени домена: night-play.ru — антикафе настольных игр):

- **главный сервер** — https://домен/ (и резервный домен), http перенаправляет на https, порт 443 занят
  витриной и подключениям не выдаётся. Тот же сайт видит любой, кто «прощупывает» входы Reality;
- **ноды** — http://IP/ (443 у нод принадлежит Reality и показывает соседний сайт).

Сертификаты продлеваются через этот же nginx (webroot). Отключить: `defaults.hardening.cover_site: false`.

## Бэкапы и перенос главного сервера

- **Бэкап** — кнопка «Сделать бэкап сейчас» (или `xui-fleet backup`). В архив попадает база 3x-ui,
  выгруженная самой панелью (клиенты, подключения, ноды, настройки), и файлы, от которых она
  зависит: сертификат домена, ключ токенов нод. Хранятся последние 10 в постоянной папке на Mac `~/Library/Application Support/xui-fleet/backups` (не зависит от того, где лежит проект; переопределяется переменной `XUI_FLEET_BACKUP_DIR`), кнопка «Открыть папку» открывает её в Finder.
  Бэкап делается сам перед каждым изменением и при запуске интерфейса, если последнему больше 12 часов.
- **Перенос** — «Перенести главный сервер…» (или `xui-fleet migrate-master НОВЫЙ_IP`). Сервис пробует
  взять свежий бэкап со старого сервера, а если тот недоступен — последний сохранённый; ставит 3x-ui на
  новый сервер, восстанавливает всё и приводит ноды и каскады в порядок. Затем смените A-запись домена
  на новый IP и нажмите «Домен подписки». Старый сервер не изменяется.
- **Проверить подключения** — прогоняет трафик через каждую ссылку подписки с главного сервера.
  Из российского дата-центра; домашние сети и мобильные операторы могут вести себя иначе.

## Перенос со старого сервера

Бэкап базы 3x-ui (`.db`) переносится одной командой:

```bash
.venv/bin/xui-fleet import-backup путь/к/бэкапу.db --node ИМЯ_НОДЫ --label "🇬🇧 UK" --dry-run
```

Без `--dry-run` выполняет перенос. Клиенты попадают на главную панель с теми же
UUID, subId, лимитами и трафиком; подключения старого сервера воссоздаются на ноде
с теми же ключами Reality (занятый порт заменяется свободным); подключения старых
нод заменяются каскадом; WARP получает на новой ноде собственную регистрацию; путь
подписки берётся как на старом сервере. Повторный запуск ничего не дублирует.

## Консоль (необязательно)

Всё то же доступно командами: `.venv/bin/xui-fleet --help`. Интерфейс вручную:
`.venv/bin/xui-fleet ui`.

## Команды

| Команда | Что делает |
| --- | --- |
| `apply` | Приводит серверы и панель к `fleet.yaml`. Идемпотентна, можно запускать сколько угодно раз. |
| `plan` | Показывает, что изменит `apply`, ничего не меняя. |
| `node add NAME HOST` | Записывает ноду в конфиг и применяет только её. |
| `node remove NAME` | Убирает ноду с мастера и из конфига (сам сервер не трогает). |
| `node list`, `status` | Ноды из конфига / живое состояние с мастера. |
| `user add NAME`, `user list` | Создать пользователя на всех подключениях / ссылки подписок. |
| `upgrade` | Обновляет 3x-ui до `panel.version`: сначала ноды, потом мастер. |
| `ui` | Веб-интерфейс. |
| `forget-host NAME` | Забыть SSH-ключ хоста после переустановки сервера. |

## SSH-доступ

- Ключ: `ssh.key: ~/.ssh/id_ed25519` (рекомендуется).
- Пароль: `ssh.password_env: MY_VAR` и `export MY_VAR=...` перед запуском. Пароль
  в файл не попадает.
- Пользователь — `root` или любой с `sudo` без пароля.
- Ключ хоста запоминается при первом подключении; при его смене сервис откажется
  подключаться.

## Что важно знать

- **Пользователи.** `users:` в конфиге — только стартовый список. Дальше ими удобно
  управлять в панели: любой клиент, который есть хотя бы на одном подключении
  сервиса, автоматически получает все новые ноды (`clients.sync_all`).
- **`fleet-bridge`** — служебный клиент, через него RU-сервер ходит на ноды.
  Не удаляйте его.
- **Ключи Reality не ротируются**: при изменении порта или SNI ссылки пользователей
  продолжают работать после обновления подписки.
- **Сертификаты.** Нода получает самоподписанный сертификат, мастер закрепляет его
  отпечаток. Мастеру нужен доверенный сертификат, иначе приложения не скачают
  подписку: `tls.mode: ip` (Let's Encrypt на IP) или `domain`; оба требуют
  открытый порт 80. Если выпуск не удался, панель получит самоподписанный
  сертификат, а `apply` предупредит.
- **SNI для Reality** задаётся в `defaults.direct.reality` / `defaults.cascade.reality`
  или у конкретной ноды. Значения по умолчанию (`www.microsoft.com` для нод,
  `ya.ru` для входа в RU) — отправная точка; подберите под свой хостинг.
- **Секреты** лежат в `.xui-fleet/state.json` (права 600): API-токены и ключи
  хостов. Файл можно потерять — токены перевыпустятся при следующем `apply`.
- **Существующая панель** не переустанавливается: сервис подключается к ней и
  добавляет только свои объекты (теги `fleet-*`).

## Проверено и не проверено

Проверено сквозным прогоном на трёх чистых Ubuntu 24.04 (systemd, SSH) с настоящим
3x-ui v3.11.0: установка с нуля, регистрация нод, каскад и прямые подключения с
реальным трафиком через Xray-клиент (TCP+Vision и XHTTP), повторный запуск без
изменений, добавление и удаление ноды, обновление, восстановление после потери
`state.json`.

Интерфейс проверен в браузере на том же стенде: настройка главного сервера,
добавление и удаление сервера, создание пользователя.

Не проверялось на реальных серверах: выпуск Let's Encrypt (`tls.mode: ip|domain`),
`hardening.firewall` (ufw), вход по SSH-паролю и через sudo, другие дистрибутивы.
