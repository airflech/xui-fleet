# Архитектура и ТЗ

## ТЗ (промт, по которому построен сервис)

> Построй инструмент, который по одному декларативному файлу разворачивает и
> поддерживает сеть 3x-ui: главная панель на RU-сервере и произвольное число
> зарубежных нод.
>
> 1. **Автонастройка сервера.** По SSH-доступу превратить чистый VPS в готовую
>    панель 3x-ui: установка закреплённой версии без вопросов, TLS, API-токен.
>    Уже установленную панель не переустанавливать, а подключать.
> 2. **Авторегистрация.** Новая нода сама появляется на RU-мастере: запись ноды,
>    входящее подключение на ней, подключение всех существующих пользователей.
> 3. **Каскад.** Для каждой ноды на RU-мастере создаётся вход, трафик которого
>    уходит на эту ноду: клиент → RU → нода → интернет.
> 4. **Одна подписка.** Пользователь получает одну ссылку со всеми подключениями
>    (каскадными и прямыми), новые ноды появляются в ней сами.
>
> Требования к качеству: идемпотентность (повторный запуск ничего не ломает и
> ничего не меняет), сбой одного сервера не останавливает остальные, секреты не
> попадают в конфиг и в аргументы процессов, никаких правок базы панели в обход
> API, ручные настройки пользователя в панели сохраняются, новый транспорт
> добавляется одним профилем.

## Ключевое решение: опираться на штатные возможности 3x-ui v3

В 3x-ui v3 уже есть всё нужное, поэтому сервис ничего не изобретает поверх:

| Задача | Штатный механизм 3x-ui |
| --- | --- |
| Установка без вопросов | `install.sh` с `XUI_NONINTERACTIVE=1` и закреплённым тегом |
| Мастер управляет нодой | встроенные **ноды**: `POST /panel/api/nodes/add`, токен с областью `node-admin` |
| Inbound на ноде | `POST /panel/api/inbounds/add` с `nodeId` — мастер сам доставляет его на ноду |
| Общие пользователи | клиенты — отдельная сущность, привязываются к любым inbound-ам (`clients/add`, `bulkAttach`) |
| Одна подписка | сервер подписок мастера отдаёт ссылки всех inbound-ов клиента, включая размещённые на нодах |
| Каскад | outbound + правило маршрутизации в шаблоне Xray мастера (`/panel/api/xray/update`) |

Сервис — это тонкий оркестратор: SSH для подготовки сервера, дальше только API
главной панели.

## Схема каскада

Для ноды `de-1` создаются:

| Объект | Где | Тег |
| --- | --- | --- |
| Inbound VLESS+Reality | на ноде (через мастер, `nodeId`) | `fleet-direct-de-1` |
| Inbound VLESS+Reality | на мастере, порт из `cascade_ports` | `fleet-cascade-de-1` |
| Outbound VLESS → нода | шаблон Xray мастера | `fleet-out-de-1` |
| Правило `inboundTag → outboundTag` | шаблон Xray мастера, сразу после правила `api` | — |

Мастер авторизуется на ноде служебным клиентом `fleet-bridge`. Правило каскада
ставится выше остальных, чтобы трафик каскада никогда не вышел напрямую с RU.
Outbound собирается из параметров самого inbound-а ноды (ключ, shortId, SNI,
транспорт), поэтому рассинхронизация невозможна.

## Модули

| Файл | Ответственность |
| --- | --- |
| `config.py` | Схема `fleet.yaml` (pydantic), значения по умолчанию, правка YAML без потери комментариев |
| `state.py` | Локальные секреты: API-токены, ключи SSH-хостов |
| `ssh.py` | Запуск скриптов от root (скрипт идёт через stdin), туннель до порта панели |
| `provision.py` | Подготовка сервера: установка, сертификат, токен, BBR, ufw |
| `panel.py` | Клиент REST API 3x-ui |
| `xrayconf.py` | Чистые функции: inbound, outbound, слияние шаблона Xray, профили транспорта |
| `reconcile.py` | Приведение мастера к конфигу: ноды → inbound-ы → каскад → клиенты → подписки |
| `engine.py` | Оркестрация: параллельная подготовка нод, затем reconcile |
| `cli.py` | Команды |

## Как достигается надёжность

- **Идемпотентность.** Каждый шаг сначала читает фактическое состояние. Объекты
  сервиса находятся по тегу `fleet-*`; всё остальное в панели не трогается.
- **Источник правды — панель.** Локально хранятся только токены и ключи хостов.
  Ключи Reality, порты, UUID читаются с мастера при каждом запуске.
- **Изоляция сбоев.** Ноды готовятся параллельно; ошибка одной попадает в отчёт,
  остальные применяются.
- **Проверка результата.** После применения мастер опрашивает каждую ноду; если
  не достучался — предупреждение с причиной.
- **Безопасность.** До панели мастера сервис ходит через SSH-туннель на
  `127.0.0.1`. Мастер проверяет сертификат ноды по закреплённому отпечатку,
  снятому по SSH, а не по сети. Токен ноды ограничен областью `node-admin`.
  Токены передаются через stdin, не через аргументы команд.

## Как расширять

- **Новый транспорт:** добавить `Profile` в `xrayconf.PROFILES` и, если это не
  TCP/XHTTP, ветку в `outbound_for_inbound`.
- **Несколько RU-входов, балансировка:** каскадный inbound на мастере — обычный
  inbound; у 3x-ui есть балансировщики подписок и outbound-ов.
- **Telegram-бот или веб-интерфейс:** вызывать `engine.Fleet` (`apply`,
  `add_user`, `status`) — CLI лишь тонкая обёртка над ним.
- **Цепочка из трёх звеньев:** нода 3x-ui может сама управлять нодами; правило
  каскада на промежуточной ноде строится тем же `merge_template`.
